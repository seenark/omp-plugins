# Upstream Sync

How to update something this repo takes from another project. Vocabulary (Upstream, Pinned Revision, Vendored Content, Adaptation, Excluded) is defined in `CONTEXT.md`.

Pick the branch:

- **Vendored Content**: Caveman, Ponytail, pstack. Upstream files are copied into a package. pstack is generated by a sync script and has its own section below.
- **External runtime**: Headroom server, RTK binary. Nothing is copied; a running program is upgraded.

## Vendored Content

| Package | Upstream | Pinned Revision and file list |
| --- | --- | --- |
| `packages/caveman` | `https://github.com/JuliusBrussee/caveman` | `packages/caveman/THIRD-PARTY-NOTICES.txt` |
| `packages/ponytail` | `https://github.com/DietrichGebert/ponytail` | `packages/ponytail/THIRD-PARTY-NOTICES.txt` |
| `packages/pstack` | `https://github.com/cursor/plugins` (`pstack/`) | `packages/pstack/THIRD-PARTY-NOTICES.txt` |

The notices file is the single source of truth for the Pinned Revision and the vendored file list. The package README lists Adaptations and Excluded parts. The numbered steps below are for Caveman and Ponytail; for pstack skip to the next section.

1. Read the Pinned Revision and file list from the notices file.
2. Clone Upstream into `/tmp`, check out the target (latest `main` unless the user names a tag), and record its full SHA.
3. Diff old against new for every vendored file, Upstream's license files (`LICENSE*`, `NOTICE`, `LICENSING.md`), and the Upstream code our package mirrors (Caveman: mode aliases and deactivation phrases; Ponytail: `hooks/ponytail-instructions.js`, `hooks/ponytail-config.js`, `pi-extension/index.js`).
4. Classify the diff. **Wording only**: continue. **Structural**: stop and report to the user before changing anything. Structural means a Mode Level added, removed or renamed; a vendored file moved, split or merged; a changed command, alias or deactivation phrase; a changed license.
5. Copy the vendored files byte-for-byte, then reapply the Adaptations listed in the README.
6. Update mirrored code to match step 3, then update the notices file (SHA, file list, license text) and the README Pinned Revision.
7. Run `bun run verify`, then start `omp` with the feature and switch through every Mode Level and `off`.

Done when every vendored file matches the new Pinned Revision, the notices file and README name it, verify passes, and the user has a short list of behavior changes.

## pstack

`packages/pstack` is generated: `bun run sync` rewrites `skills/` and `agents/` from Upstream at the Pinned Revision in `upstream.json`, applying the Adaptations in `src/sync/rules/*.ts`. Never edit a vendored file by hand and never copy Upstream files across: change a rule, or add a fork entry, and re-run the sync. The package README describes the rule groups.

Run everything from `packages/pstack`. Skills and agents named `pstack-*` in `agents/` come from the role table (`bun run generate:agents`), not from Upstream.

### Stop and ask the owner

Before running the sync with a new `--rev`, diff old against new in an Upstream checkout (`git clone https://github.com/cursor/plugins /tmp/cursor-plugins`, then `git -C /tmp/cursor-plugins diff --name-status <pinned>..<target> -- pstack/skills pstack/agents pstack/plugin.json pstack/LICENSE cursor-team-kit/skills/deslop cursor-team-kit/LICENSE`). Stop and report to the user, changing nothing, when the diff shows:

- a skill or playbook added, removed or renamed (give your classification of each new skill from the run below as the proposal);
- a new Cursor primitive: a tool name, command, path, frontmatter key or product feature that no Adaptation rule or term category in `src/sync/rules/` mentions (read the added lines; the term scan cannot see what no category names);
- a new skill-name collision: the report lists skills whose name another discovered skill directory already owns (run with `--skill-dir <directory>` for each, such as `~/.agents/skills`);
- a license change in either `LICENSE` file.

**Wording-only fast path.** When every changed line is prose in a file pstack already ships, nothing above applies, and the report in step 2 has no conflicts, no new term, and no new skill, do not ask: finish steps 1 to 6 and give the user a short list of what changed.

### Update run

1. Read the Pinned Revision in `upstream.json`. Choose the target SHA (latest `main` unless the user names a tag), run the stop-and-ask diff above.
2. Run `bun run sync --rev <target> --upstream /tmp/cursor-plugins --report /tmp/pstack-sync-report.md`. With no `--rev` it re-syncs the current pin. The sync writes `skills/`, `agents/`, `upstream.json` and the notices block, deletes files the rules no longer produce, and exits 1 on conflicts. Read the report:
   - **Conflicts**: resolve per fork kind below.
   - **New skills to classify**: place each in one class. *Workflow-called*: another vendored skill or playbook names it (`grep -r "<name>" skills`); it ships. *Standalone*: a user invokes it directly and `poteto-help` lists it; it ships. *Cursor-only*: it needs a Cursor product (a webhook bot, the Cursor UI); add an exclusion with a reason in `rules/core.ts` and a rule that drops every row or link pointing at it. Ask the owner before applying a classification, per the stop conditions.
   - **Skills sync removes**: confirm the owner agreed to the removal.
   - **Remaining Cursor-specific terms** and **terms the verify gate rejects**: add or extend a rule in the group that owns the primitive (`dispatch.ts`, `pr.ts`, `sessions.ts`, `core.ts`) until the gate list is empty. Match the OMP equivalent; do not delete meaning.
   - **Rules that matched nothing**: a rule whose Upstream text vanished; remove or rewrite it.
3. The `/<name>` form of every skill in the run (Upstream skill directories after exclusions and renames) is rewritten to `/skill:<name>` by `sessions/skill-slash-form`, so a skill Upstream adds needs no list edit and one run is enough. Then re-run step 2: the sync is idempotent.
4. Run `bun run generate:agents` if the vendored agents or role table changed, then `bun run verify` from the repo root. Its `check:sync` step re-runs the sync read-only at the pin and fails, naming each path or term, on a vendored file that differs from the sync output without a fork entry, a stale file, a conflict marker, or any Cursor-specific term not covered by an `allowances` entry. Fix the rule or fork, never the vendored file.
5. Smoke: start `omp` with the package, run `/skill:poteto-help`, and run `/skill:<name>` for each skill the bump added.

Against the current pin, `bun run sync --upstream /tmp/cursor-plugins` writes nothing, reports no conflicts, no new skills and no gate failures, and `bun run verify` passes. If it does not, something drifted: find it with `bun run check:sync`.

### Forks

The fork entries (`path`, `kind`, `reason`, `since`) in the rule groups are the Fork Registry (CONTEXT.md, ADR-0009): each marks a file as ours. The sync merges Upstream changes by kind:

- `patched`: our small edit to an Upstream file. Upstream changes are 3-way merged against the old pin; overlapping edits leave `<<<<<<<` markers that you resolve by hand. Verify fails while markers remain.
- `rewritten`: a file replaced or written by us (it may not exist in Upstream). Ours always wins. When Upstream changes it, the report names a conflict: read the Upstream diff, update our text if it matters, and continue. The conflict does not repeat once the pin moves.

A new file under `skills/` or `agents/` that Upstream does not have needs a `rewritten` fork entry. Without one, `check:sync` calls it stale.

### Term allowances

An `allowances` entry (in the group that owns the category) tolerates one known leftover term until the ticket that removes it lands. It names the file, term and exact count. When the term goes, the entry no longer matches and the gate fails until the entry is deleted, so allowances cannot outlive their ticket. Leave none behind at publish.

## External runtime

### Headroom server

The repo `compose.yaml` is the source of truth for the homelab deployment (`ssh local-ubuntu-server`, directory `~/headroom`, secrets in `.env`, which is never committed).

1. Read the Upstream `CHANGELOG.md` between the running version and the target. Look for breaking items: renamed or removed env vars, bind or auth policy, license, image variants.
2. Confirm the image exists: `docker manifest inspect ghcr.io/headroomlabs-ai/headroom:<version>-code-nonroot`.
3. Confirm every safety env var in `compose.yaml` still exists in the new image: grep each name under the image's `site-packages/headroom`. The reasons are in `docs/research/headroom-0.40-agent-pitfalls.md`.
4. Back up state on the homelab with `docker run --rm -v ~/.headroom:/d:ro -v ~:/out alpine tar czf /out/headroom-backup-<date>.tgz -C /d .`, and copy `compose.yaml` aside.
5. Edit the repo `compose.yaml`, copy it to the homelab, and run `docker compose up -d` while no OMP session is mid-task, because a restart drops Headroom's session caches.
6. Verify:
   - `/health` reports the new version.
   - Logs show `Code-Aware: ENABLED`.
   - `docker exec headroom env` lists the safety vars.
   - `POST /v1/compress` with `config.session_id` returns a `session` block.
   - A `read` tool result comes back with `router:excluded:tool`.

### RTK binary

1. `HOMEBREW_NO_AUTO_UPDATE=1 brew upgrade rtk`, and read the Upstream changelog for rewrite rules, filters that can hide failures, and tracking changes.
2. Check that the contract `packages/rtk` relies on still holds:
   - `rtk rewrite` exit codes (0 or 3 rewrite, 1 or 2 leave unchanged), checked on `git status`, `cargo test`, `go test ./...` and `bun test`.
   - `RTK_DB_PATH` and `RTK_RECALL_DB` are honored.
   - The `commands` table columns are the ones read in `packages/rtk/src/store.ts`.
3. Adjust the guard list in `packages/rtk/src/rewrite.ts` and the minimum version if needed, then run `bun run verify`.
4. Smoke: start `omp`, run one rewritten command, and watch the RTK segment change.
